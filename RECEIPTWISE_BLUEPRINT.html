1. Product Vision

Mission Statement

Empower users to understand, track, and optimize their spending through intelligent receipt processing and proactive financial insights.

Core Value Proposition

Transform passive receipt collection into active financial awareness without the complexity of traditional budgeting apps.

Target Users

  • Budget-conscious professionals who want spending visibility
  • Users with multiple credit cards seeking reward optimization
  • Anyone frustrated with manual expense tracking
  • People who keep receipts but never organize them

Key Differentiators

  • Receipt-first: Start from actual purchases, not bank feeds
  • Card-aware: Understand and optimize credit card rewards
  • Proactive: Surface insights before users ask
  • Honest AI: Never hallucinate financial data
  • Privacy-first: User owns their data

2. Core User Journeys

First-Time User
  1. Sign up with email/OAuth
  2. Onboarding explains core concept
  3. Add credit cards (optional)
  4. Set monthly budget (optional)
  5. Upload first receipt
  6. AI extracts and categorizes

  8. Dashboard shows transaction

Daily Receipt Upload

  2. AI processes (<5 seconds)

  4. Confirm or edit details
  5. Transaction saved and categorized
  6. Dashboard updates real-time
  7. Insight generated if significant

10. Receipt Processing Pipeline

1. UPLOAD        → User uploads image/PDF
2. VALIDATE      → Check file type, size (<10MB)
3. STORE         → Upload to S3 with signed URL
4. OCR + EXTRACT → GPT-4o vision extracts all fields
5. CATEGORIZE    → AI categorizes transaction
6. MATCH PAYMENT → AI matches to user's cards (or asks)
7. PREVIEW       → Show extraction with confidence scores
8. USER CONFIRM  → User reviews/edits before saving
9. SAVE          → Transaction saved to database
10. INSIGHT      → Generate insight if significant

11-13. Bank Integration & Reconciliation (V3)

Note: Bank integration is V3 functionality. MVP uses manual receipt upload only.

Integration Architecture

  • Use Plaid Link for secure bank connection
  • Store Plaid access tokens encrypted (never in frontend)
  • Sync transactions via webhook or daily pull
  • Map Plaid categories to internal categories
  • Handle token refresh automatically

Transaction Reconciliation Strategy

  • Match by: Amount (exact) + Date (±1 day) + Merchant (fuzzy)
  • 3/3 match: Auto-link receipt to bank transaction
  • 2/3 match: Suggest to user for confirmation
  • 1/3 match: Ignore, log for manual review
  • Never delete receipt data when bank transaction found
  • Mark reconciled transactions to prevent re-matching

14. Card Benefits Architecture

Verified Benefits

From official card databases or APIs. Used for recommendations with high confidence.

User-Entered Benefits

Manually entered by user. Used for recommendations with clear attribution.

CRITICAL RULE: The system will NEVER claim a card provides a specific benefit unless that benefit is in the verified database or user-entered. AI suggestions are clearly labeled and NOT used for recommendations.

15. Notification Architecture

Notification Types

  • Spending Alert: Above daily/weekly average
  • Budget Warning: Approaching or exceeding budget
  • Insight: Pattern detected, recommendation
  • System: Account, security, features

Delivery Rules

  • Max 3 notifications per day (excluding system)
  • Deduplicate similar insights within 24 hours
  • Prioritize actionable over informational
  • User can snooze notification types
  • Channels: in-app (always), email, push (V2)

16. Security Architecture

Authentication & Authorization

  • JWT tokens in HTTP-only, Secure, SameSite=Strict cookies
  • Password hashing with bcrypt (cost factor 12+)
  • Email verification for sensitive operations
  • Session timeout: 7 days inactive, 30 days absolute
  • Rate limiting on auth endpoints (5 attempts/15 min)
  • OAuth 2.0 with PKCE for social login

Data Protection

  • TLS 1.3 for all connections (HTTPS only)
  • Database encryption at rest (AES-256)
  • Receipt images encrypted at rest in S3
  • Signed URLs with short expiration (15 min)
  • Financial tokens never exposed to frontend

API Security

  • Input validation with Zod on all endpoints
  • Rate limiting: 100 req/min general, 10 req/min AI
  • CORS restricted to known origins
  • CSRF protection with double-submit cookie
  • Request size limits (10MB for receipts)
  • SQL injection prevention via Prisma ORM

Compliance Considerations

  • GDPR: Data deletion, export, consent management
  • CCPA: Similar privacy rights for California
  • PCI DSS: Not storing card numbers (only last 4)
  • SOC 2: Audit logging, access controls, encryption

29-30. AI Hallucination Prevention

CRITICAL: Financial applications have ZERO tolerance for AI hallucinations. These strategies are mandatory.
StrategyDescription
Tool-Based Data AccessAI MUST use function tools to access financial data. Never answer from "memory".
Structured OutputsUse OpenAI structured outputs with JSON schemas for all extraction tasks.
Confidence ScoresEvery AI extraction includes confidence score. Low confidence triggers user review.
Source AttributionAI responses reference specific transactions, dates, and amounts from database.
Explicit UnknownsAI must say "I don't have that information" rather than guessing.
User ConfirmationAll AI extractions shown to user before saving. User can edit any field.

31-32. Receipt & Payment Method Matching

Payment Method Matching Flow

  1. Extract Payment Info: AI extracts payment text from receipt (card type, last 4 digits)
  2. High Confidence Match: Last 4 digits AND card network match → auto-assign
  3. Medium Confidence Match: Only card network matches one card → ask user
  4. Low Confidence Match: Generic card type with multiple options → user must choose
  5. No Match: No payment info or no cards registered → ask user to select or skip
CRITICAL RULES:
  • NEVER silently assign a payment method without sufficient evidence
  • NEVER make up payment method information
  • When in doubt, ASK THE USER
  • Store confidence level with transaction for future reference

33-35. Bank Matching, Notifications & AI Data Access

Bank Transaction Matching (V3)

  1. Get bank transaction from Plaid
  2. Search receipts: amount (exact) + date (±2 days) + merchant (fuzzy)
  3. Score: 3/3 = auto-link, 2/3 = suggest, 1/3 = log for manual
  4. Mark both as reconciled to prevent re-matching
  5. Keep receipt data even if bank transaction exists (receipts have more detail)

Notification Generation

  1. Event triggers notification check (transaction save, scheduled job)
  2. Query relevant data (spending, budgets, patterns)
  3. AI generates user-friendly message (structured output)
  4. Check user preferences and rate limits
  5. Save notification and dispatch to channels

AI Data Access (Secure)

The AI assistant NEVER has direct database access. All data retrieval happens through typed, validated tool functions with user_id filtering.
  1. User asks question in chat
  2. AI determines which tool(s) to call
  3. Tool functions validate user ownership
  4. Query executes with user_id filter (always)
  5. Results returned to AI as structured data
  6. AI formulates response citing actual data
  7. Response includes source attribution
